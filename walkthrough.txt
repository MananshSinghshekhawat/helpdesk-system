## 4. Core Data Flow Diagrams

### 4.1 AI Reply Generation Pipeline

```mermaid
sequenceDiagram
    participant UI as Frontend
    participant API as /ai/suggest
    participant AI as ai_service
    participant RAG as rag_service
    participant Qdrant as Qdrant DB
    participant LLM as Groq LLM
    participant DB as MySQL

    UI->>API: POST /tickets/{id}/ai/suggest
    API->>DB: Verify ticket exists + org match
    API->>AI: generate_ai_draft(ticket_id, agent_type)
    AI->>DB: Get ticket + messages
    AI->>DB: Find active AI agent by type
    AI->>RAG: retrieve_context(org_id, agent_id, query)
    RAG->>DB: Get KB vector metadata (agent + common)
    RAG->>DB: Get ticket vector metadata
    RAG->>Qdrant: search_vectors (3 sources)
    Qdrant-->>RAG: Scored points
    RAG->>RAG: Merge + Rerank (70% similarity + 20% confidence + 10% recency)
    RAG-->>AI: Top-K context chunks
    AI->>LLM: generate_groq_reply(subject, message, context)
    LLM-->>AI: Generated reply text
    AI->>AI: Calculate confidence score
    AI->>DB: Save AIDraft + AIInvocationLog
    AI-->>API: AIDraft object
    API-->>UI: {draft_id, draft_text, confidence_score}
```

### 4.2 Email Ingestion Pipeline

```mermaid
sequenceDiagram
    participant Trigger as POST /mailbox-sync
    participant Proc as mailbox_processor
    participant IMAP as email_reader_service
    participant Gmail as Gmail IMAP
    participant ETS as email_ticket_service
    participant DB as MySQL

    Trigger->>Proc: process_mailboxes(db)
    Proc->>DB: list_active_mailboxes()
    loop For each mailbox
        Proc->>IMAP: fetch_unread_emails(mailbox)
        IMAP->>Gmail: IMAP4_SSL connect + login
        IMAP->>Gmail: SEARCH UNSEEN
        Gmail-->>IMAP: Email IDs
        loop For each email
            IMAP->>Gmail: FETCH (RFC822)
            IMAP->>IMAP: Parse headers (From, Subject, Message-ID, In-Reply-To, References)
            IMAP->>IMAP: Extract body (text/plain or html→text)
            IMAP->>Gmail: Mark as SEEN
        end
        IMAP-->>Proc: List of email dicts
        loop For each email
            Proc->>ETS: create_ticket_from_email(email_data)
            ETS->>DB: Find/Create Customer
            ETS->>DB: Thread detection (In-Reply-To → message_id lookup)
            ETS->>DB: Fallback: References header → message_id lookup
            alt Thread match found
                ETS->>DB: Add message to existing ticket
            else New conversation
                ETS->>DB: Create new Ticket + first message
            end
        end
    end
```

### 4.3 Agent Reply + Email Send Flow

```mermaid
sequenceDiagram
    participant UI as Frontend
```

### Key Model Fields

| Model | Key Columns | Notes |
|-------|-------------|-------|
| **Ticket** | `id, organization_id, customer_id, channel(email/web/api), subject, status(new/assigned/in_progress/waiting/escalated/resolved/closed), message_id, current_owner_type(human/ai), ai_enabled` | `message_id` stores the email Message-ID for thread matching |
| **TicketMessage** | `id, ticket_id, sender_type(customer/human/ai/system), sender_id, message_body, message_id, is_internal_note` | `message_id` stores the SMTP Message-ID for reply threading |
| **Customer** | `id, organization_id, name, email, phone` | Deduplicated by email per org |
| **AIAgent** | `id, organization_id, name, type(router/delivery/sales/billing/support), confidence_threshold, is_active` | Configurable threshold for auto-reply gating |
| **AIDraft** | `id, ticket_id, ai_agent_id, draft_text, confidence_score, is_sent, sent_at` | Stores all AI-generated suggestions |
| **KnowledgeBase** | `id, organization_id, name, scope(common/agent), agent_id` | `scope=agent` ties KB to specific AI agent |
| **KnowledgeDocument** | `id, organization_id, knowledge_base_id, title, type, status(uploaded/processing/indexed/failed), content` | Full extracted text stored in `content` |
| **KBVectorMeta** | `id, organization_id, knowledge_base_id, document_id, chunk_index, chunk_text, qdrant_point_id, confidence_weight` | Maps DB ↔ Qdrant vector IDs |
| **Skill** | `id, organization_id, name, endpoint_url, http_method, auth_type(none/api_key/oauth), timeout_ms` | External API integration definition |
| **RoutingRule** | `id, organization_id, intent, ai_agent_id, ai_enabled, ai_mode(suggest_only/auto_reply), priority, active` | Intent → Agent routing |
| **Mailbox** | `id, email, password, imap_host, imap_port, department, is_active` | **Missing `organization_id`** |

## 7. RAG (Retrieval-Augmented Generation) Deep Dive

The RAG system in [rag_service.py](file:///c:/Users/adity/cqhelper/helpdesk_api/app/services/rag_service.py) retrieves context from **3 sources**:

| Source | Purpose | Filter |
|--------|---------|--------|
| **Agent-specific KB** | Knowledge docs uploaded to agent's own KB | `scope=agent` + `agent_id=X` |
| **Common KB** | Shared organizational knowledge | `scope=common` |
| **Similar Tickets** | Historical resolved tickets | `TicketVectorMeta` |

**Reranking Formula:**
```
score = 0.70 × cosine_similarity + 0.20 × confidence_weight + 0.10 × recency_score
```

> [!WARNING]
> **Placeholder Embeddings!** The `generate_embedding()` function uses **SHA-256 hash** as a fake embedding — NOT a real embedding model. This means vector search results are essentially random. This must be replaced with a real embedding model (e.g., OpenAI `text-embedding-3-small` or `sentence-transformers`) before production.
